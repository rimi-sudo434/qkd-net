# qkd-net

## Getting Started

Please refer to the [`disable-spring-auth` branch README](https://github.com/Open-QKD-Network/qkd-net/blob/disable-spring-auth/README.md) for the relevant setup instructions.

## Overview

The OpenQKDNetwork project aims to provide a reference implementation of a [four-layer Quantum Key Distribution (QKD) network solution](https://openqkdnetwork.net). Two sample applications are also provided to demonstrate how an application can fetch and use keys generated by a QKD network.

The project adopts a flexible, layered architecture that follows [SOLID principles](https://en.wikipedia.org/wiki/SOLID).

A microservice-based architecture is used for software design and implementation. One benefit of this approach is the flexibility it provides when deploying the system in production.

**The project was originally compiled and tested successfully on Ubuntu 16.04 and Linux Mint 18.3 with Java 8. Changes may be required to run it in other environments, including different operating systems and Java versions.**

## Layers

The system consists of the following layers:

1. Key Management System (KMS)
2. Quantum Network Layer (QNL)
3. Quantum Link Layer (QLL)

The fourth layer is the User (or Host) Layer. It belongs to the client of this system and is therefore beyond the scope of this project.

QKD devices belong to the QLL. A vendor-specific glue layer may be required to integrate QKD devices with the other layers until an international standard, such as ETSI or ITU-T, for the interface is widely adopted.

### Key Management System (KMS)

The KMS layer provides an application interface for fetching keys used in symmetric cryptography. How these keys are used is the responsibility of applications in the User Layer.

The KMS layer comprises the following microservices:

1. Configuration Service
2. Registration Service
3. Authorization Service
4. KMS Service
5. KMS API Gateway Service
6. KMS QNL Service

### Quantum Network Layer (QNL)

The QNL is the core component that extends QKD technology from point-to-point communication to network-level communication. It sits between the KMS layer and the QLL.

The QNL provides key blocks to the KMS after fetching them from the QLL. This keeps the KMS layer independent of the underlying QKD technology.

The QNL currently consists of a single microservice:

1. Key Routing Service

The Key Routing Service contains routing and key-relaying modules that respond automatically and promptly to changes in the QKD network topology. It pushes key blocks to the KMS QNL Service and also responds directly to requests from the KMS Service for key blocks.

### Quantum Link Layer (QLL)

Ideally, the QLL consists of operational QKD devices. This project provides a QLL simulator for situations in which real QKD-device links are unavailable, such as a planned satellite-based QKD link between geographically distant nodes.

## Prerequisites

Install the following software before proceeding. Ensure that the required executables are available in your system's `PATH`.

1. Java SDK 8 or later: [Java downloads](https://www.oracle.com/java/technologies/downloads/)

1. `curl`

## Quick Start Guide

The following steps describe how to set up a two-node system on two Linux (Ubuntu) machines.

Assume the following IP addresses:

* Node A: `192.168.2.207`
* Node B: `192.168.2.212`

### 1. Set Up Node A

Run the following commands on Node A:

```bash
git clone https://github.com/Open-QKD-Network/qkd-net.git
cd qkd-net
cd kms
./scripts/build
```

The build process generates the `~/.qkd` directory. If you already have configuration files in this directory, back them up before removing anything.

If you intend to start with a clean configuration, remove the generated directory:

```bash
rm -rf ~/.qkd
```

**Warning:** This command permanently removes the `~/.qkd` directory and its contents. Use it only if you are certain that you do not need those files.

Return to the repository root and extract the configuration archive:

```bash
cd ..
tar xvf qkd-kaiduan-a.tar
```

If the archive extracts a `.qkd` directory into the current directory, copy or move that directory into your home directory, taking care not to overwrite configuration files you want to keep.

Update the file `~/.qkd/qnl/routes.json` on Node A so that Node B's IP address is correct:

```json
{
  "adjacent": {
    "B": "192.168.2.212"
  },
  "nonAdjacent": {}
}
```

### 2. Set Up Node B

Repeat the build and configuration preparation steps on Node B.

Extract the configuration archive for Node B:

```bash
tar xvf qkd-kaiduan-b.tar
```

Place the extracted `.qkd` directory in Node B's home directory, taking care not to overwrite existing configuration files.

Update `~/.qkd/qnl/routes.json` on Node B:

```json
{
  "adjacent": {
    "A": "192.168.2.207"
  },
  "nonAdjacent": {}
}
```

### 3. Start the KMS Services

On both Node A and Node B, run:

```bash
cd qkd-net/kms
./scripts/run
```

Keep the services running while testing the sample application.

### 4. Build and Run the TLS Demo

The example uses Alice on Node A and Bob on Node B.

On Node A, run:

```bash
cd qkd-net/applications/tls-demo
make
```

On Node B, open `src/bob.c` and update the `site_id` function to match the node IP addresses:

```c
static char* site_id(char* ip) {
    if (strcmp(ip, "192.168.2.212") == 0)
        return "B";
    else if (strcmp(ip, "192.168.2.207") == 0)
        return "A";
    else
        return "C";
}
```

Then build the application on Node B:

```bash
cd qkd-net/applications/tls-demo
make
```

Start Bob on Node B:

```bash
./bob -b 10446
```

Start Alice on Node A:

```bash
./alice -i 192.168.2.212 -b 10446 -f ./data/whale.mp3
```

If the setup is successful, Alice should connect to Bob and retrieve the required key from the KMS. The output should include messages indicating a successful connection and key retrieval.

On Node B, the received file should be saved in `bobdemo`. The output should indicate that Bob is listening for incoming connections, that the key has been retrieved, and that the TLS connection has closed.

*Note: Exact output may vary depending on the configuration and software versions.*

## Setting Up a Three-Node Network

To set up a three-node network, extract `qkd-kaiduan-c.tar` on Node C.

Assume the following IP addresses:

* Node A: `192.168.2.207`
* Node B: `192.168.2.212`
* Node C: `192.168.2.235`

The network topology is:

```text
A <----> B <----> C
```

Add Node C to the adjacent nodes in Node B's `~/.qkd/qnl/routes.json` configuration file:

```json
{
  "adjacent": {
    "A": "192.168.2.207",
    "C": "192.168.2.235"
  },
  "nonAdjacent": {}
}
```

Ensure that the configuration on each node matches the intended network topology.

# Correctly Handle Configuration Files

This is a distributed, multi-layer system that uses several configuration files to support deployment across different nodes or sites. Check these files carefully before running or testing the system.

## `kms.conf`

The sample applications, including qTox and `tls-demo`, require a `kms.conf` file under the `$HOME/.qkd` directory.

You can create this file manually with the following entries:

```text
http://localhost:9992/uaa/oauth/token
http://localhost:8095/api/newkey
http://localhost:8095/api/getkey
C
```

Depending on where the KMS node is deployed, replace `localhost` with the IP address of the host running the KMS layer.

The last line represents the KMS site ID. Update it to match the correct site ID; `C` is only an example.

## `config-repo`

The `config-repo` directory under `$HOME` contains the configuration property files required by the microservices.

These files originate from:

```text
qkd-net/kms/config-repo
```

They are copied to `$HOME/config-repo` and maintained in a local Git repository.

## `site.properties`

This file is located at:

```text
qkd-net/kms/kms-service/src/main/resources/site.properties
```

The following example explains some of the site-specific configuration properties used by the KMS Service:

```properties
# Number of keys per block
kms.keys.blocksize=1024

# Size of a key in bytes
kms.keys.bytesize=32

# Base directory for storing key blocks
kms.keys.dir=${HOME}/.qkd/kms/pools/

# IP address of the host running the Key Routing Service
qnl.ip=localhost

# Port on which the Key Routing Service listens for key-block requests
qnl.port=9292
```

## `config.yaml` — KMS QNL Service

This file is located at:

```text
qkd-net/kms/kms-qnl-service/src/main/resources/
```

It is copied to:

```text
$HOME/.qkd/kms/qnl/
```

The KMS QNL Service uses this configuration file.

Example properties:

```yaml
# Port on which the KMS QNL Service listens
port: 9393

# Size of a key in bytes
keyByteSz: 32

# Number of keys in a block
keyBlockSz: 1024

# Location where the KMS QNL Service stores key blocks
poolLoc: kms/pools
```

## `config.yaml` and `routes.json` — Key Routing Service

### `routes.json`

This file is located in:

```text
qkd-net/qnl/conf/
```

It is copied to:

```text
$HOME/.qkd/qnl/
```

The file contains network topology information. Adjacent (neighboring) nodes are configured manually, while non-adjacent nodes are discovered by the routing module.

The `adjacent` section maps each neighboring node's name to its IP address.

Example configuration for Node B:

```json
{
  "adjacent": {
    "A": "192.168.1.101",
    "C": "192.168.1.103"
  },
  "nonAdjacent": {}
}
```

### `config.yaml`

This file is located in:

```text
qkd-net/qnl/conf/
```

It is copied to:

```text
$HOME/.qkd/qnl/
```

It contains configuration parameters for the Key Routing Service, which operates at the network layer.

Example:

```yaml
# Base location for configuration files and other paths
base: .qkd/qnl

# Route configuration file name
routeConfigLoc: routes.json

# Location where QLL stores key blocks for QNL
qnlSiteKeyLoc: qll/keys

# Unique identifier for this site
siteId: A

# Port on which the Key Routing Service listens for key-block requests
port: 9292

# Size of a key in bytes
keyBytesSz: 32

# Number of keys in a block
keyBlockSz: 1024

# Number of keys in a QLL block
qllBlockSz: 4096

# IP address of the host running the KMS QNL Service
kmsIP: localhost

# Port on which the KMS QNL Service listens
kmsPort: 9393

# One-Time Pad (OTP) key configuration
OTPConfig:
  # Number of keys per block
  keyBlockSz: 1024

  # Location of the OTP key block
  keyLoc: otp/keys
```

## Test the KMS Service

OAuth is enabled, so you must obtain an access token before calling the API.

The following example uses the project's documented sample credentials. Do not use sample credentials in a production environment.

```bash
curl -X POST \
  -H "authorization:Basic aHRtbDU6cGFzc3dvcmQ=" \
  -F "password=bot" \
  -F "client_secret=password" \
  -F "client=html5" \
  -F "username=pwebb" \
  -F "grant_type=password" \
  -F "scope=openid" \
  http://localhost:9992/uaa/oauth/token | jq
```

A successful request returns JSON similar to:

```json
{
  "access_token": "<access-token>",
  "token_type": "bearer",
  "refresh_token": "<refresh-token>",
  "expires_in": 43017,
  "scope": "openid"
}
```

Use the returned access token when calling the API endpoints.

Assume that two sites are configured with site IDs `A` and `B`. An application at Site A initiates a connection to an application at Site B.

The two API endpoints below demonstrate how pre-shared keys can be fetched.

## 1. New Key

An application at Site B calls the `newkey` endpoint.

**Request**

* Method: `POST`
* URL path: `/api/newkey`
* URL parameter: `siteid`, an alphanumeric site identifier (for example, `siteid=A`)

Example:

```bash
curl 'http://localhost:8095/api/newkey?siteid=A' \
  -H "Authorization: Bearer <access-token>" | jq
```

Example response:

```json
{
  "index": 28,
  "hexKey": "a2e1ff3429ff841f5d469893b9c28cbcb586d55c8ecf98c83c704824e889fc43",
  "blockId": "133ad3f8de6cc9da"
}
```

The response contains the key index, the key in hexadecimal format, and the ID of the block containing the key.

## 2. Get Key

An application at Site A calls the `getkey` endpoint using information returned by the `newkey` request.

Because the sites are different, the application at Site A must first obtain its own OAuth access token.

**Request**

* Method: `POST`
* URL path: `/api/getkey`
* URL parameters:

  * `siteid`: the requesting site's identifier (for example, `siteid=B`)
  * `index`: the key index
  * `blockid`: the ID of the block containing the key

Example:

```bash
curl 'http://localhost:8095/api/getkey?siteid=B&index=1&blockid=' \
  -H "Authorization: Bearer <access-token>" | jq
```

Example response:

```json
{
  "index": 1,
  "hexKey": "4544a432fb045f4940e1e2fe005470e1a35d85ede55f78927ca80f46a0a4b045",
  "blockId": "8a94dc22e761de8c5501addc05"
}
```

The actual values returned by the API depend on the current configuration and available keys.
